# 37NDEST Repository Structure

## Repository Layout Rules

### Root Level
- `AGENTS.md` — Operating contract for all agents
- `README.md` — Project overview and quick start
- `package.json` — Node.js project metadata
- `.gitignore` — Git exclusion rules
- `.kiro/` — Kiro configuration and guidance
- `specs/` — Feature specifications
- `docs/` — Project documentation
- `data/` — Content and data files
- `public/` — Static assets
- `src/` — Application source code
- `scripts/` — Build, validation, and utility scripts
- `tmp/` — Temporary scratch space (not committed)

### No Root-Level Clutter
- Do not create unnecessary root-level clutter; standard toolchain configuration files at root are acceptable
- Do not create temporary files at root
- Do not create feature-specific folders at root
- All feature work maps to `specs/` or `src/features/`

## Content Placement Rules

### Canonical Deck Content
- **Location:** `data/decks/canonical/`
- **Format:** JSON (source of truth)
- **Ownership:** User-maintained, version-controlled
- **Immutability:** Never modified by app runtime
- **Validation:** Validated through deterministic validation scripts during import workflows and other quality checks as needed
- **Backup:** Committed to repository

### Derived Content
- **Location:** `data/decks/derived/`
- **Purpose:** Generated subsets, transformations, exports
- **Ownership:** Generated by scripts, not hand-edited
- **Regeneration:** Can be safely deleted and regenerated
- **Versioning:** May or may not be committed (document decision)
- **Dependency:** Always derived from canonical content

### Raw Imports
- **Location:** `data/decks/imports/`
- **Purpose:** Staging area for raw imported artifacts
- **Format:** TSV, APKG, or other source formats
- **Ownership:** External sources
- **Processing:** Transformed to canonical JSON by scripts
- **Cleanup:** Can be deleted after successful import

### Schema Definitions
- **Location:** `data/schema/`
- **Purpose:** JSON schema and validation artifacts for content and import structures
- **Format:** JSON Schema and related validation artifacts
- **Ownership:** Maintained with specs
- **Usage:** Validates canonical content and runtime structures

### Schedule Configuration
- **Location:** `data/schedule/`
- **Purpose:** Pacing and schedule configuration
- **Format:** JSON
- **Ownership:** User-maintained or generated
- **Usage:** Loaded at runtime for pacing recommendations

## Spec Placement Rules

### Spec Folder Structure
```
specs/
├── 001-foundation/
│   ├── requirements.md
│   ├── design.md
│   └── tasks.md
├── 002-deck-import/
│   ├── requirements.md
│   ├── design.md
│   └── tasks.md
└── NNN-feature-name/
    ├── requirements.md
    ├── design.md
    └── tasks.md
```

### Spec Naming
- Use numeric prefix: `NNN-feature-name`
- Prefix indicates sequence/priority
- Feature name in kebab-case
- Folder name is the spec identifier

### Spec File Requirements
- `requirements.md` — User-facing requirements and acceptance criteria
- `design.md` — Technical design and architecture
- `tasks.md` — Implementation task list with checkboxes

### Spec Ownership
- One spec per feature or major work item
- Specs are durable and should not be deleted casually
- Active specs are the execution source of truth for non-trivial implementation, within the broader repository source-of-truth hierarchy
- All non-trivial work must map to a spec

### Spec Lifecycle
- Create spec before implementation
- Update spec as requirements clarify
- Completed specs should remain durable and should not be deleted casually
- Reference spec in all related code changes

## Code Organization Rules

### Source Code Structure
```
src/
├── app/                    # App shell, routing, main entry
├── components/             # Reusable React components
├── features/               # Feature-specific logic
│   ├── profiles/           # Profile management
│   ├── deck-import/        # Deck import feature
│   ├── review/             # Review/study feature
│   ├── schedule/           # Scheduling feature
│   └── settings/           # Settings feature
├── lib/                    # Shared utilities and helpers
├── db/                     # IndexedDB schema and queries
├── hooks/                  # Custom React hooks
├── types/                  # TypeScript type definitions
├── styles/                 # Global styles, tokens, and style helpers as needed
└── test/                   # Test utilities and fixtures
```

### Feature Folder Organization
- Each feature folder contains related logic
- Feature organization should align with active specs where practical, without requiring a rigid one-to-one mirror
- Feature folders may contain feature-specific components, hooks, utilities, types, and tests when the feature is large enough to justify local ownership

### Shared Utilities (src/lib/)
- Only place utilities here if used by multiple features
- Document ownership and purpose
- Avoid dumping unrelated utilities
- Keep lib/ focused and minimal

### Type Definitions (src/types/)
- Global types and interfaces
- Shared domain models
- Feature-specific types in feature folders
- Keep types close to usage

### Hooks (src/hooks/)
- Custom React hooks
- Feature-specific hooks in feature folders
- Shared hooks in src/hooks/
- Document hook dependencies

### Tests (src/test/)
- Test utilities and fixtures
- Test setup and configuration
- Feature-specific tests in feature folders
- Keep tests close to code

## Script and Data Rules

### Validation Scripts
- **Location:** `scripts/validation/`
- **Purpose:** Validate canonical content, schemas, data integrity
- **Ownership:** Maintained with specs
- **Execution:** Run before import or deployment
- **Output:** Clear pass/fail with error details

### Import Scripts
- **Location:** `scripts/import/`
- **Purpose:** Transform raw imports to canonical format
- **Ownership:** Maintained with deck import spec
- **Execution:** Deterministic and auditable
- **Output:** Canonical JSON in `data/decks/canonical/`

### Report Scripts
- **Location:** `scripts/reports/`
- **Purpose:** Generate statistics, summaries, diagnostics
- **Ownership:** Maintained as needed
- **Execution:** Optional, for analysis only
- **Output:** Reports or summaries

### Script Discipline
- Scripts must be deterministic
- Scripts must be auditable
- Scripts must document their purpose
- Scripts must validate input and output
- Scripts must fail clearly on error

## Temporary File Rules

### Temporary Scratch Space
- **Location:** `tmp/`
- **Purpose:** Experiments, prototypes, one-off tests
- **Ownership:** Not committed to repository
- **Cleanup:** Can be deleted without impact
- **Constraint:** Must not become silent dependencies

### Temporary File Discipline
- Do not commit files to `tmp/`
- Do not reference `tmp/` from production code
- Do not rely on `tmp/` for build or deployment
- Do not use `tmp/` for long-term storage
- Clean up `tmp/` regularly

### Experiments and Prototypes
- Use `tmp/` for experimental code
- Document purpose clearly if the experiment is complex, reusable, or operationally important
- Move to proper location if successful
- Delete if abandoned

- **Ownership:** Maintained with specs

- **Ownership:** Maintained as needed
- **Usage:** Quick lookup for standards and resources

## File Creation and Modification Rules

### Before Creating a New File
1. Determine its category (code, data, spec, doc, script)
2. Identify the correct folder
3. Follow naming conventions
4. Document purpose clearly when the file is complex, reusable, or operationally important
5. Update this structure guide if adding a new persistent folder

### Before Modifying Existing Files
1. Check if file is version-controlled
2. Check if file is canonical content
3. Check if file is generated (regenerate instead of edit)
4. Document reason for change
5. Update related specs if needed

### File Naming Conventions
- **Specs:** `NNN-feature-name/`
- **ADRs:** `NNNN-decision-title.md`
- **Scripts:** `descriptive-name.js` or `descriptive-name.ts`
- **Data:** `descriptive-name.json`
- **Components:** `ComponentName.tsx`
- **Hooks:** `useHookName.ts`
- **Types:** `TypeName.ts` or inline in files

### File Headers
- Use file headers selectively for scripts, unusual configuration files, migrations, or complex operational files
- Include purpose and important usage notes when that context will help future agents
- Do not require boilerplate headers on ordinary application source files

## Important Rules (Explicit)

### Canonical Content Discipline
- Canonical deck JSON belongs under `data/decks/canonical/`
- Derived outputs never replace canonical content directly
- Raw imports go to `data/decks/imports/`
- Validation and transformation logic belongs in `scripts/`

### Product Decision Discipline
- Product decisions do not belong in random chat logs
- Product decisions belong in steering, specs, or ADRs
- Decisions must be documented before implementation
- Decisions must be discoverable by future agents

### Non-Trivial Work Discipline
- Non-trivial work must map to a spec folder
- Specs must exist before implementation
- Implementation must reference spec
- Completed work must be recorded in spec tasks

### Temporary File Discipline
- Temporary experiments belong in `tmp/`
- Temporary files must not become silent dependencies
- Temporary files must not be committed
- Temporary files must be cleaned up

### Feature Logic Discipline
- Keep feature logic grouped by domain
- Feature organization should align with active specs where practical, without requiring a rigid one-to-one mirror
- Feature-specific code stays in feature folders when practical
- Shared code moves to `src/lib/` only if reused across features

### Utility Discipline
- Avoid dumping unrelated utilities into `src/lib/`
- Document ownership and purpose of utilities
- Keep `src/lib/` focused and minimal
- Move utilities to feature folders if only used there

## Governance and Consistency

### Repository Governance
- This structure guide is the authoritative source for repository layout and file placement within the broader repository source-of-truth hierarchy
- All agents must follow this structure unless an approved spec, ADR, or steering update explicitly changes it
- Structure changes require decision-log entry
- Structure changes must be documented here

### Future Consistency
- New features must follow this structure
- New scripts must follow this structure
- New documentation must follow this structure
- Structure violations must be corrected

### Audit and Cleanup
- Periodically audit repository structure
- Move misplaced files to correct locations
- Remove orphaned or unused files
- Document structural changes in decision log
